# Official/open bulk alley-width research — HCMC

Observed 17 October 2026. No commit, no Gemini, no account creation, no message sent, and **zero new requests to the limited planning point endpoint**. Existing work and running crawlers were left alone.

**No anonymously accessible, licensed, current citywide Clear Width dataset was established.** Two real official bulk sources were found and imported as dated metadata: the public HCMGIS Phước Long A WFS and the official Quận 9 gazette annex. They add metadata to **295 unique cached OSM ways**, including **192 named/tagged alleys**, and add **zero ways to current Clear Width coverage**. This is a useful partial import and a concrete route to request fuller data, not a replacement for current surveys.

The Quận 9 annex was published with QĐ 01/2009/QĐ-UBND dated 16 February 2009. The gazette says it is partly amended by QĐ 09/2012/QĐ-UBND. The 2012 amendment specifies an 8 m ROW for a final section of Đường 21 renamed Hẻm 301; the section cannot be unambiguously assigned to an OSM way from the published decision alone, so it remains review-only. The historical import never claims current legal validity for every row. The generic city QĐ 88/2007 minima were repealed by QĐ 563/QĐ-UBND on 26 January 2026; those minima were not used to generate any width.

Parsing uses PDF table cells and headers across all 13 layouts/wards, including the two-column existing/proposed ROW layout in Long Bình. Vietnamese decimal commas and width ranges are preserved; no LLM or OCR guessing was used. PDF page 3 was rendered and visually checked against the separated base-width and future-ROW columns. All numbered rows that contain at least one width are audited: 935 imported, zero rejected numeric rows; one escape-alley row has no historical base width and retains only its explicit ROW. Every source row keeps its page, ordinal and original numeric cells.

Text correspondence reuses `common.norm_name`, `listings_city.graph_for` and the established `app.live._match`. Only an explicit complete alley/street chain can match. Coordinate-free matching first rejects source-name collisions across wards and OSM names in multiple distant clusters; all candidate way centres must lie in the former Q9/Thủ Đức area. Parent fallback is rejected for widths. Very common unnamed/number-only alleys and changed road names remain unresolved. Same-name OSM splits within one ≤500 m cluster may share a historical name-level record; this does not certify the present entire segment or prove matching precision.

WFS matching uses the source geometry and cached OSM, with a local metre approximation: way length at least 15 m, ≥90% sampled positions and ≥90% length within 3 m of the source, maximum distance ≤5 m, ≥80% local direction comparisons within 20°, and exactly one qualifying source feature. Crossings and competing parallel candidates are rejected. No map pixels become geometry. The imported matches are research correspondences with explicit method statistics, not verified survey alignments.

## Access, terms and request discipline

The public HCMGIS application itself lists the relevant layers and requests their WFS service for ordinary data/map display. GetCapabilities advertises WFS `GetFeature`, `Fees=NONE` and `AccessConstraints=NONE`. The bounded export requests fetched at most 1,000 features each and confirmed complete returned totals of 355, 288, 250 and 250 for the target layers. That establishes anonymous service availability and intended public GIS use; it does **not** establish an explicit open-data redistribution licence. Reuse terms must be clarified before externally redistributing original geometries. The import contains dated factual width/ROW metadata and OSM IDs; it does not republish WFS geometries.

One administrative-boundary candidate, `thuduc:bdy_phuong`, returned only the capped first 1,000 of 30,380 unnamed boundary segments. It was rejected as a ward-identity aid, was not paginated, and is not represented as a complete boundary dataset. The similarly named `mohinhgis_thuduc` alley layers returned the same 288/250 feature counts and did not demonstrate citywide coverage.

Robots checks precede direct research requests. The accessible HCMGIS map/service, gazette and city open-data hosts returned robots 404; no disallow rule was bypassed. Hosts with robots transport errors were left unavailable. HTTPS certificate verification stayed on; the HCMGIS GeoNode host has a hostname mismatch and the main HCMGIS host a self-signed certificate in this environment. There was no TLS bypass, proxy, IP change, user-agent rotation, CAPTCHA solving, login, token extraction or undocumented auth workaround.

The newer DPA ArcGIS app publicly requests raster MapServer tiles. That is intended public viewing, not permission for mass feature extraction. Directory/MapServer metadata checks returned empty HTTP 200 responses; its advertised parcel FeatureServer metadata returned JSON application `statusCode:401` despite HTTP 200. The host was marked stopped and no further API probes were made. No attempt was made to use application/browser credentials. The [DOST official explainer](https://dost.hochiminhcity.gov.vn/chuyen-doi-so/thanh-pho-ho-chi-minh-ban-hanh-quy-che-quan-ly-khai-thac-nen-tang-ban-do-so-dung-chung/) says organisations and individuals require authorised accounts for the shared spatial platform.

The city open-data dataset itself reports **licence unspecified**, and its [site terms](https://opendata.hochiminhcity.gov.vn/dieu-khoan-su-dung) require written permission for copying/distribution/cooperation. Its downloaded “1:2000 data” attachment is a **data dictionary**, not a feature collection. A catalogue title and a modern upload date do not establish a usable dataset.

The raw archive records **68 direct-request metadata entries**, including robots and transport failures; separate web-search/tool browsing and ordinary browser resource loads are not included in that count. Direct download batches used identified, sequential requests with a 2-second spacing policy within each batch; metadata timestamps record the actual individual attempts. No bulk point sampling, high-rate tile sweep, retry storm or second crawler was introduced. Existing saved portal research was examined offline to avoid repeating unsuccessful probes.

## Reproduce and inspect

```sh
python3 pipelines/official_bulk_fetch.py
python3 pipelines/official_bulk.py build
python3 pipelines/verify_official_bulk.py
python3 pipelines/render_official_bulk.py
PYTHONPATH=backend:. python3 -m unittest backend.tests.test_official_widths pipelines.test_official_bulk -q
```

The fetcher is bounded by `data/official/official-bulk-downloads.json`, uses an identified contact user agent, checks robots, spaces requests, keeps immutable responses, verifies normal TLS, and persists HTTP/application 401/403/429 refusals. It does not refresh existing successful bodies automatically. The recorded SHA256 values identify this research snapshot; a fresh server export can change timestamps/content and requires source/date review. `build` is offline and uses the current existing OSM inventory; regenerate that inventory separately with the repository workflow if it becomes stale. No build stage loads Gemini keys or invokes an LLM.

The loader exposes `official_width_records` in each `WidthRange` JSON. Every record is tagged `tier:Official` **and** `affects_clear_width:false`, carries original source date, metadata meaning, URL and rights note, and remains outside the tier combiner. Atomic publication and mtime/size refresh invalidate cached API serialization; a malformed replacement retains the last good product and deletion removes metadata. It contributes neither strongest-width tier nor resolved-fit counts. The decision and justification are [D49](../decision-log.md). No process was restarted or deployment performed.
